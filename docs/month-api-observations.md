## 官方帖子发现：三个栏目都能匿名读取

路径为 `POST https://api.kurobbs.com/forum/companyEvent/findEventList`，表单参数如下：

| 参数 | 含义 |
| --- | --- |
| `gameId=3` | 鸣潮 |
| `eventType=1` / `2` / `3` | 活动 / 资讯 / 公告 |
| `pageNo` | 从 1 开始 |
| `pageSize=30` | 本次核验每页数量 |

本次三个 `eventType` 均返回业务 `code=200`。`data.list` 包含 `postId`、`postTitle`、`publishTime` 和 `firstPublishTime`；两个时间字段本次均为毫秒 Unix 时间戳。

**不能见到一条旧帖子就停止发现。** 列表并不按 `publishTime` 严格递减排列。例如资讯第 4 页包含 2026-09-30 发布的“3.7 版本建议反馈收集贴”，却排在第 3 页的一些 9 月 21 日帖子之后。只读取前 3 页会漏掉这个重要研究入口。

本次读取范围：活动 2 页、资讯 5 页、公告 2 页，每页 30 条。资讯第 5 页发布时间范围为 2026-08-28 至 2026-09-14；活动第 2 页、公告第 2 页均已早于研究窗口。这个有界检查提供了实用候选清单，**不证明全社区帖子或评论已经穷尽**。接口部分响应出现 `hasNextPage=true`、`pages=1`、`total=-1` 并存，不能把 `pages=1` 当成只有一页。

## 日期：哪些能精确知道，哪些需要推定

### 一级评论没有核验到隐藏的精确时间

`/forum/comment/getPostCommentListV2` 的本次一级评论对象只有展示字段 `commentTime`，例如 `09-30`、`10-22`，未见 `createTime` 或其他精确时间戳字段。完整旧日期也可能出现，例如 `2023-07-26`。

`/forum/comment/getReplyList` 返回的 `data.postComment` 父评论也只有同样的 `commentTime`，并未因读取楼中楼而补全一级评论时间。不能把回复自己的时间当成父评论时间。

楼中楼 `data.replys` 中则核验到了 `createTime` 毫秒时间戳。本次 3 条近月回复的 `createTime` 换算到 UTC+08:00 后均与 `replyTime=09-30` 一致。此类记录可以精确到接口提供的时间精度过滤。

### 推荐的透明处理规则

1. 保留 `time_raw`，不覆盖原始展示值。
2. 有有效 Unix 时间戳的记录，使用时间戳并记录 `time_source=api_timestamp`。
3. 有完整年月日但没有时分秒的记录，记录 `precision=day`，不要伪造成真实零点发布时间。
4. 对 `MM-DD`：可依据同帖已知的官方发布时间至采集时间建立候选区间；只有其中恰有一个合法年月日时，才标记为**区间假设下的推定日期**。建议分别存储 `inferred_date`、`time_source=display_mmdd_unique_within_post_lifetime` 和 `precision=day`。
5. 栏目的 `publishTime/firstPublishTime` 未经证明就是底层帖子的首次创建时间。使用它作为区间下界属于明确的研究假设，必须在报告中披露。若展示日期早于这个下界，或存在多个年份候选，保留未知；不能据此断定该评论在窗口外或强行补当前年。
6. 相对时间只有在语义和采集时间锚点明确时才可处理，否则留未知。日期未知记录不纳入声称为“近一个月”的核心统计，单列排除数量。
7. 按日精度恢复的日期可以参与日期窗口判断和按日汇总；起止日若只覆盖当天一部分，应说明边界不确定性。不要声称它们拥有精确发布时间。

报告至少区分：原始时间戳、完整日期、推定日期、日期未知四类。另记录日期窗内、窗外和未知数量，保持可审计。

### 不用 ID 推算日期作为纳入依据

少量交叉核验发现，4 条带权威 `createTime` 的回复，其 `createTime - (replyId >> 22)` 均约为 `1420041600000`，偏差在 1 秒以内，符合某类 Snowflake 时间编码特征。但是未找到官方对位移、epoch、时钟或所有 ID 类型作出的格式保证；帖子 ID 的生成也明显可能早于栏目发布。

因此 ID 可以辅助发现明显矛盾，**不能作为本次补年份、确定一级评论精确时间或决定近月纳入的唯一证据**。不能把某个看似合理的 ID 解码结果描述成官方返回的时间。

## 详情接口与官网一手依据

从官网实际加载的 [comment-reply-dialog-BMYg4x0A.js](https://web-static.kurobbs.com/resource/prod/assets/comment-reply-dialog-BMYg4x0A.js) 核对到帖子详情请求参数为：

```json
{"postId":"帖子ID","isOnlyPublisher":0,"showOrderType":2}
```

该脚本通过 [useConfig-DLqk4N_9.js](https://web-static.kurobbs.com/resource/prod/assets/useConfig-DLqk4N_9.js) 的接口封装调用 `/forum/getPostDetail`。对建议反馈帖按这个形状匿名实测，仍返回业务 `code=102`、`msg=服务器外部错误`。这不证明一定需要登录，也不能伪称已经获得底层帖子创建时间、总评论数或完整帖子正文。未继续猜测签名或绕过限制。

脚本同样将父评论的 `commentTime` 直接展示在页面上，没有发现网页额外恢复精确父评论时间的逻辑。接口未来可能改版，以上结论仅对应本次核验。

进一步的研究结果应以最终采集清单、日期归类、文本清理和人工编码为准。关键词命中只能说明提及主题，不能直接推出负面意见、优先级或全体玩家的需求。
