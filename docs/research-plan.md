# 鸣潮玩家评论研究：角色反馈与优化问题

这是一份可执行的个人研究计划。项目将公开评论作为发现研究线索的资料，先整理“大家在讨论什么”，再通过人工阅读和必要的访谈核实具体问题。只有亲自完成相应工作后，才能将它写为简历经历。

> `examples` 或 `demo` 命令生成的内容是合成演示数据。它可以展示技术流程，不能充当真实玩家评论、访谈记录或研究发现。

## 1. 先把研究范围写成一句话

填写以下研究声明，再开始选帖：

> 我研究【具体角色／明确的一组角色】在【版本或活动】期间的角色体验，以及相关讨论中的性能、稳定性和设备适配反馈。资料来自【选定库街区帖子】，评论时间为【开始时间】至【结束时间】，均按 UTC+08:00 解释。

建议第一次只研究一个熟悉的角色和一段明确的时间窗口，避免把不同版本、设备和角色的反馈混在一起。“角色反馈”与“优化问题”是两个观察维度，并不意味着每条优化评论都在评价所选角色。

分别记录“帖子围绕该角色”和“评论文本直接提到该角色”。只凭帖子主题，不能把每条评论都归因于该角色；使用角色名筛选评论时，也可能漏掉昵称、代称和省略主语的回复。筛选口径应在报告中说明。

## 2. 研究问题

1. 在纳入的角色讨论中，玩家分别提到了哪些机制、操作手感、养成、强度和角色表现话题？
2. 人工阅读后，哪些评论确实描述了具体问题？问题发生在什么场景，有没有设备、版本或操作条件？
3. 优化相关讨论涉及帧率、发热、闪退、网络、画面加载和适配的哪些方面？哪些反馈缺少可复现条件？
4. 官方帖与社区帖中，讨论主题的分布是否不同？这种差异是否可能来自帖文内容、评论排序或采样范围？
5. 哪些线索值得进一步访谈或做可用性测试？需要补什么证据，才能提出改进建议？

本项目不以“证明某角色设计失败”或“证明优化已经改善”为预设目标。自动输出也不提供满意度和情感评分。

## 3. 选帖与抽样

### 官方帖与社区帖分开记录

| 来源 | 可选材料 | 适合观察 | 主要偏差 |
|---|---|---|---|
| 官方帖 | 角色展示、版本说明、已知问题或优化说明 | 公告触发的话题、期待和回应 | 评论可能集中于公告内容；活动奖励可能影响留言 |
| 社区帖 | 实际体验、攻略、设备测试、问题讨论 | 具体场景、分歧和使用经历 | 主题可能偏向抱怨或高热度事件；不代表所有玩家 |

建议起步时每类来源选择少量帖子，并包含不同立场或主题。这里是研究设计建议，不是已经完成的采样数量。不要只挑标题负面、点赞最高或支持自己看法的帖子。

建立一张选帖表，可使用表格软件，至少记录：

| 字段 | 填写内容 |
|---|---|
| 帖子标识与链接 | 能回到原始上下文的公开链接 |
| 来源类型 | 官方／社区；无法确认时写“待确认” |
| 纳入原因 | 为什么与本次研究问题有关 |
| 角色、版本、主题 | 可确认的信息；不要凭空补全 |
| 发布时间与研究窗口 | 区分帖子时间、评论时间和实际采集时间 |
| 排序与采集上限 | 记录实际获取的排序、页数、评论上限 |
| 回复范围 | 是否包含楼中楼；根评论与回复是否分别检查 |
| 采集状态 | 完整／达到上限／接口受限／部分失败 |

如果不同来源的评论数量差异很大，应分别报告各来源的条数和主题比例。不要直接用总评论数比较“官方玩家”和“社区玩家”的态度；同一用户也可能同时出现在两类帖子中。

### 时间窗口

- 事先固定起止时间，并记录时区；不要分析完后才选择有利的时间范围。
- 如果比较某次版本或角色调整前后，可以设计长度接近的窗口，并记录分界事件。分界日当天计入后段，具体以工具输出说明为准。
- 前后窗口帖子主题、选帖数量和采集方式尽量一致。若做不到，说明差异，不把它解释为版本造成的效果。
- 无效或缺失时间的评论仍可做主题阅读，但不进入日统计或前后对比；报告这部分条数。
- 先检查采集到的最早与最晚评论日期。帖子发布于窗口内，不代表其全部评论也在窗口内。

只使用正常可访问的公开内容。遇到登录、验证码或访问限制时，按工具提示使用自己的正常会话或手动导出资料，不绕过访问控制。仅保留研究所需的内容和匿名标识，报告中避免展示可识别的个人信息。

## 4. 清洗与分析流程

1. **检查来源**：确认是真实采集数据还是演示数据，保存采集记录；如发生分页中断，应写明。
2. **清理资料**：检查空文本、重复记录、重复评论标识和异常时间，分别记录原始条数、删除原因与保留条数。相同文本可能来自不同用户，是否删除应有明确规则。
3. **限定范围**：按事先确定的帖子、评论时间和角色口径筛选。保留排除理由，避免事后挑选。
4. **运行主题规则**：检查 `summary.json`、`topics.csv`、`daily_counts.csv` 和 `labeled_comments.csv`。
5. **人工核验**：填写 `review_sample.csv`，回看源帖与上下文，补充主题或记录误判。
6. **修订并复跑**：修改 `config/topics.json` 中的关键词；保存修改前后版本和原因。
7. **撰写研究报告**：将统计、原文证据与人工解释分开，列出局限和后续验证计划。

采集上限是控制工作量的设置，不等于对全部评论的随机抽样。没有采到某个问题，也不能据此说玩家没有这个问题。

## 5. 词典如何人工核验

默认词典覆盖角色机制、操作手感、养成资源、强度数值、角色表现，以及帧率卡顿、发热耗电、稳定性、网络、画面加载、设备适配和其他优化提及。具体命中词在结果文件中可检查。

关键词命中只说明“提到了这个话题”。以下都是说明规则局限的虚构示例，不是采集结果：

| 示例评论 | 规则可能识别 | 人工需要判断 |
|---|---|---|
| “现在没有卡顿了，手感也不错” | 帧率与卡顿、操作与手感 | 提到了卡顿，但没有在报告当前卡顿问题 |
| “听说某机型会闪退，我还没遇到” | 设备适配、闪退与稳定性 | 属于转述，不能当作该用户亲历问题 |
| “这个角色真的太吃资源了” | 可能漏掉养成主题 | 检查语境，再决定是否加入表达词 |
| “强度还好，主要是技能循环不顺” | 强度与数值、角色机制 | 区分一般提及与实际抱怨的部分 |

### 填写 `review_sample.csv`

保留原始字段，在空白的人工字段中标注：

| 字段 | 如何填写 |
|---|---|
| `rule_topics` | 工具的原始主题结果，保留以便比较 |
| `matched_keywords` | 工具的命中词，保留以便定位误判 |
| `manual_topics` | 阅读后确认的主题名称；多项用 `；` 分隔；无相关主题写“无相关主题”；无法确定写“待确认” |
| `contains_explicit_problem` | 填“是／否／无法判断”；只有原文明确报告具体问题时才填“是” |
| `manual_notes` | 写明证据短语、肯定／否定／转述、角色、设备、场景，以及判断不确定之处；未知信息留空或写未知 |
| `review_status` | 阅读后改为“已核验”；需要上下文或复核时写“待复核” |

未提到设备，就不要推测是手机或 PC；“卡”也可能表示卡池、卡关，需要上下文。评论里同时谈角色和掉帧，不自动意味着该角色引发掉帧。

工具选取的是最多 60 条的确定性主题覆盖样本，包含命中、交叉命中和未命中的例子。它便于找错，但不是概率样本。建议：

- 同时阅读命中和未命中评论，检查误报与漏报。
- 若有条件，请另一位阅读者独立标注部分评论，再讨论分歧；只有一人时，如实写明。
- 为新关键词记录来源和修改理由，避免为了提高命中数而无限扩大词典。
- 如需评价整体分类表现，应另外设计并保留独立的随机验证样本、明确标签标准，再计算指标。当前报告没有完成这项验证，不应写“准确率达到某数值”。

## 6. 指标和分母

| 指标 | 定义 | 不能解释为 |
|---|---|---|
| 纳入评论数 | 清洗并按研究口径筛选后进入分析的评论条数 | 玩家人数、活跃用户数 |
| 主题命中评论数 | 至少命中一个关键词主题的评论数，一条只计一次 | 有问题或不满意的玩家数 |
| 某主题提及占比 | 该主题命中的评论数 ÷ 全部纳入评论数 | 该问题在全部玩家中的发生率 |
| 同组提及数 | 同一大类中按评论去重，例如一条同时谈帧率和发热，在优化组中只计一次 | 各子主题计数直接相加 |
| 多主题评论数 | 同时命中两个及以上主题的评论数 | 重复采集条数 |
| 每日评论量 | 按 UTC+08:00 日期汇总的样本评论数 | 每日活跃度、所有社区讨论量 |
| 前后段主题比例 | 各时间段以各自评论数为分母计算比例 | 版本改动的因果效果 |

多标签占比之和可能超过 100%。例如，一条评论同时谈技能和掉帧，会进入两个主题；“角色反馈”和“优化相关”两组也可能重叠。没有样本的分组应写“无样本／不可比较”，而不是把零值解释为没有问题。

还需要主动说明以下偏差：

- **发帖者和评论者偏差**：愿意公开表达的人不代表沉默玩家；强烈满意或不满的人可能更愿意发言。
- **帖子与排序偏差**：问题帖、活动帖、热门排序会吸引不同的讨论。
- **同一人多次发言**：评论条数和匿名作者标识都不能直接推广为全体玩家人数。
- **上下文缺失**：楼中楼、图片、视频、表情和网络用语可能影响含义，纯文本规则无法完整理解。
- **规则分类边界**：规则识别主题，不判断情感、满意度或建议优先级；“提及”不是“诉求成立”。

## 7. 必要时补充访谈：五个核心问题

招募实际体验过相关角色或遇到相应场景的玩家。先说明研究用途、是否录音及资料如何使用，取得同意；不需要询问账号密码或无关的个人信息。问题围绕真实经历，不要求玩家支持研究者的假设。

1. **最近一次经历**：“请回忆最近一次使用这个角色的过程：当时在什么玩法中，用什么设备，想完成什么？”
2. **具体过程**：“当时哪一步最顺利，哪一步最费力？能按发生顺序讲一遍吗？”
3. **问题条件**：“如果出现过卡顿、发热或其他异常，最先观察到什么？发生前做了什么，是否再次出现？”如果没有遇到，就记录没有遇到，不引导其编造问题。
4. **影响与应对**：“这件事对那次游戏有什么实际影响？你尝试了什么办法，结果怎样？”
5. **改进与验证**：“如果只能改一件事，你最希望改什么，为什么？什么变化会让你觉得问题得到解决？”

追问“最近一次”“当时怎么做”“有什么可观察的变化”，少问“是不是很差”“如果出了功能你一定会用吗”。访谈可以帮助理解原因，少量受访者的意见不能直接换算为总体占比。

## 8. 可交付报告骨架

1. **研究背景与范围**：想支持什么决策；角色、版本、时间、来源与排除条件。
2. **资料与过程**：选帖表、采集方式、采集上限、清洗前后条数、失败或缺失情况。
3. **方法与口径**：主题词典版本、多标签分母、人工核验过程；如做了访谈，说明实际人数、招募条件和记录方法。
4. **主题分布**：图表描述样本中的提及频次，必要时按来源或时间分别展示，不自动贴正负标签。
5. **人工核实的发现**：每项发现包含原文证据、场景、适用范围与不确定性；转述和亲历分开。
6. **建议与验证**：建议针对什么问题、依据是什么、适用于谁、如何通过访谈或测试继续验证。
7. **局限**：非代表性、词典遗漏、评论语境、采样限制、无法支持的因果判断。
8. **附件**：来源清单、代码、词典、统计表、核验表与访谈提纲；分享前检查匿名处理。

建议使用证据表把观察与解释区分开：

| 观察到的原文／统计 | 人工解释 | 目前缺少什么证据 | 可执行的下一步 |
|---|---|---|---|
| 【实际证据】 | 【有依据且限定范围的解释】 | 【设备、场景或上下文等】 | 【访谈、复现或可用性测试】 |

`report.html` 是自动生成的探索报告，`key_findings.md` 是结果摘要。它们需要你的人工核验与解释，才能成为完整的研究报告。把“准备验证的假设”与“已经核实的发现”明确区分。
